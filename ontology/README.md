# F00 candidate validation profile
Frozen logical authority: [L2 freeze](../docs/architecture/l2-freeze-record.md). This is the minimum executable W1 candidate-validation subset, not a generic production knowledge engine.

## Candidate pack and authority
A module uses a human-readable per-owner JSON pack under `knowledge/Kxx/` plus a separately qualified manifest under that owner. Records are typed, stable ID + exact revision; Source IDs are global (do not copy/redefine a Source already present in a required provider pack); claims/context/evidence/case records have unique professional owner. Inventory accounts for actual frozen discovery **row identities**; a MODULE must account for every current row, including legacy duplicates and unresolved rows, but row accounting is not professional completion. CANDIDATE rows reference one or more scoped candidate claims; UNKNOWN/DISPUTED/HISTORICAL/ROUTED rows have reasons and no admitted claims. No automatic alias, equivalence or resolution.

The profile is exact Git-blob pinned by the validator. The controller supplies the expected manifest Git blob from the actual current Task/review subject, not from incoming data at query time. Each manifest binds the exact pack Git blob and explicit source-specific scope/locator/accessed URI/limits, qualified edge scope, and H obligations. The actual frozen source/case/discovery documents are checked against exact bytes/rows. F00 R2 independently binds L1 anchor path→blob to the actual frozen Git tree 96ae7e9a2ee5c000b63f001faeee4a6a4be69396 at 280d3be584ab717211b9b99925ac07705f2ab64c. The 316 eligible paths are in l1-anchor-tree.json (blob a72360e348f00e82a74809e6acc056f05b311b1f), pinned by validator. The test independently compares the complete projection with git ls-tree; the isolated public reader needs no Git object database. A new path or changed working blob cannot pass as frozen L1 even with a fresh candidate pin. Newly researched G07 sources require a separate qualified provenance authority/record type and concrete tests before use; this finite profile does not admit them as L1. A source registration or hash is identity/evidence location, not truth, rights or actual measurement. If earlier qualified revisions exist the controller must also supply a current separately pinned prior-identity checkpoint. The v2 checkpoint records canonical SHA256 of each exact record plus version-bound Source qualification and Claim semantic subject identities. Source identity binds exact qualification scope, limits, locator kind/accessed URI. Claim identity binds complete sorted outgoing relation/qualification set, associated exact case groups and views, role bindings owned by those views, and mandatory H obligations. Incoming navigation is derived, not authority. The validator refuses altered same revisions, coordinated removal/downgrade, older selected revisions, and disappearance of prior qualified subjects within a loaded owner. Retirement/invalidation is not implemented by this profile; route a distinct reviewed successor contract rather than hide history. New revisions of source/claim or associated evidence require current references and affected claim/group/view revisions, including downstream H/O changes. The prior checkpoint must be derived from the authoritative earlier candidate/qualified subject, never re-sealed from the incoming candidate. Legacy record-only checkpoints are rejected. A controller may load a subset of owners but cannot treat missing provider refs as qualified. First-ever candidate may have null prior checkpoint; the caller/controller owns currentness and must not omit existing history. New revisions require new scoped qualification/independent review, not runtime self-sealing; changes to dependent bindings and records use current exact refs.

Required knowledge H edges use specific consumer/provider/condition/provider context and group obligations, all applicable views bind support; O references are optional navigation, no converse or automatic satisfaction. Query closure follows outgoing H only, returns contextual claims, source/evidence qualification and limits, case bindings and inverse navigation. Input is private within the reader and projections detached. Unresolved query explicitly UNKNOWN. Every returned claim is CANDIDATE and conditional, acceptedClaims=0. Independent exact-head content review and integration are separate admission authority, not a validator output. F00 does not yet implement accepted overlays, production schema, full relation families or all domain capability coverage; each module must implement actual required new families and specific D2×ability tests before use or route owning contract change.

## Actual test entry
From repository root:
```sh
node tests/knowledge/f00.test.mjs
node tools/validate-knowledge.mjs tests/knowledge/fixtures/controller-input.json 356965a306773c4a555c8768d96cecad03d54972 K01-PERIOD-CENTS@1
```
Fixture input is explicitly enabled for these tests; production-shaped MODULE test uses temporary generated row accounting and does not write actual knowledge. No formal population. The CLI expected controller input blob is supplied explicitly, never computed at consumption from a mutable input. The fixture contains a conditional cross-domain composition (stable periods→frequency→cents) only to test H; it does not impose a K01→K07 task dependency. Actual module gates come from native Task DAG, and missing provider is unresolved unless correctly materialized. Independent review must evaluate each source/claim/case/obligation and exact revision context; the validator does not infer that content is true or self-qualified.
